# Merchant readiness — September 2026

Whether `paycross_flutter` is ready for a first merchant on both platforms, and
what the evidence for that actually is.

This is the campaign's document of record. It reports what was measured, at the
strength the measurement supports, and says plainly where a claim rests on
reading source rather than on running a cell. Where an earlier claim in this
campaign was overstated and later corrected, the corrected wording is what
appears here; Appendix B lists those corrections so nobody re-derives them.

**Scope, stated once.** Everything below is the PayCross **TEST** sandbox.
Nothing in this campaign touched production, on any dimension, at any point.
The one production statement in this report is a readiness gap read from
deployment state, not a test result — see "Production readiness".

---

## The headline

**69 of 69 cells pass on `main`, on both platforms, with zero measured label
divergence between them.**

| | Android | iOS |
|---|---|---|
| cells run | 38 | 31 |
| passed | **38** | **31** |
| failed / skipped / control checks | 0 / 0 / **0** | 0 / 0 / **0** |
| `host_suspended_seconds` | `0.0` on every cell | `0.0` on every cell |
| redaction scans | silent | silent |

Zero control checks is the strong form of the statement. A control check only
runs after a cell fails; none ran, so no cell ever had to prove the rig was
still honest.

Four results are worth stating before any defect, because they are the ones a
merchant is actually buying:

* **The two platforms agree.** All 31 shared cell/dimension pairs were compared
  mechanically — label shape with transaction ids normalised, plus
  `session_status`, `txn_count`, `failure_code`, `recovery`,
  `network_decline_code` and the four `threeds_result` fields. **0 divergences.**
  A merchant who integrates against one platform's behaviour will not be
  surprised by the other.
* **A stored credential is still 3-D Secure challenged on re-use**, on both
  platforms, from a form that never held a card number — full challenge round
  trip, `liability_shifted: true`, `eci 05`.
* **Lifecycle is clean.** Backgrounding a payment for 60 seconds during the
  challenge or during polling changes nothing on either platform; a rotation
  survives the SDK's activity being destroyed and recreated; a killed process
  correctly delivers no result at all and leaves the transaction short of an
  authorization.
* **R12 is disproved.** The plan predicted that an iOS 3-D Secure challenge
  makes the rest of the accessibility tree unqueryable. It does not — `cvv` and
  `payButton` stay queryable with the challenge up. Measured independently
  twice, on two branches. Nothing depended on it, but the plan header said
  otherwise and this report corrects it rather than repeating it.

What that headline does **not** cover is listed in full under "Residual risks".
The two largest: **D6 (version floors) has not run**, and **no iOS cell has ever
executed against a non-debug binary.**

## 3. What a merchant's Dart code actually sees

The full behavioural table — one row per integration error, session state,
decline, timeout and lifecycle event, with the label the app renders and the
merchant-API state behind it — is
[`outcome-table.md`](outcome-table.md). It is the document the integration
guide should be written from. The four things worth lifting into this report:

**Declines follow one pattern, and it is the same on both platforms.**
`change_method` re-arms the sheet and ends as `result:cancelled` when the
shopper gives up; `do_not_retry` is terminal and arrives as
`result:failure:do_not_retry:<txn>` directly. The recovery token in the label is
the server's own `failure.recovery` string.

**An empty `<txn>` carries meaning.** `result:failure:restart:` with nothing
after the colon separates a failure that never created a transaction from one
that did. A malformed token and a token past its `exp` are label-identical and
both empty; the *session* in the expired-JWT case is still open — only the JWT
died.

**Re-presenting a spent token does not charge twice.** It resolves as
`result:success:<txn>` against the existing transaction; the merchant API still
reports one transaction.

**Neither SDK detects a server-expired session at present time.** The shopper is
shown a normal, fully payable form with no error banner, and only learns at
submit — if then. Measured on both platforms, from the dumps directly. This is
recorded here as a merchant-facing behaviour to document rather than a filed
defect, and it is the one item in this section a reader should weigh before
launch.

## 4. Findings

Every confirmed failure — one whose interleaved control passed — became an issue
on the owning repository. Labelling them `merchant-readiness` was the campaign's
convention rather than something enforced, and four went out without it; §8
names which.

The full-matrix rerun produced one reproduction, one open question it could not
close, and one divergence no cell can reach. **That last one was filed off the
rerun** — `android#31`, opened 2026-09-01. The other two added observations to
things already on record.

### 4.1 SDK defects — Android

| id | title | strength | status |
|---|---|---|---|
| [android#23](https://github.com/paycross/payment-android-sdk/issues/23) | Retryable 3DS decline: re-armed sheet outlives the session; `Cancelled` carries no transaction id | measured | open |
| [android#25](https://github.com/paycross/payment-android-sdk/issues/25) | Poll deadline reports `Recovery.RETRY` over a succeeded, liability-shifted payment | **measured, four independent sessions** | open |
| [android#26](https://github.com/paycross/payment-android-sdk/issues/26) | Google Pay button has no test handle of its own: `testTagsAsResourceId` is never set | source + measured corroboration | open |
| [android#27](https://github.com/paycross/payment-android-sdk/issues/27) | A CVV typed for a new card is carried across to a stored card and submitted with it | **read from source; not reached by any cell** | open |
| [android#28](https://github.com/paycross/payment-android-sdk/issues/28) | A saved Amex card cannot have its 4-digit CVV entered — the saved-card path validates at 3 digits regardless of brand | **read from source; no Amex card was run** | open |
| [android#31](https://github.com/paycross/payment-android-sdk/issues/31) | `Recovery.fromString` discards the server's string for unknown values, where iOS keeps it | **read from source; unreachable from any cell** | open |

**#25 is the one a merchant cannot ignore.** `airplane_during_polling` — cutting
the network after the authorization lands — reports `result:failure:retry:<txn>`
over a payment that **succeeded and shifted liability**: session `completed`,
transaction `succeeded`, `threeds_result` `authenticated`/`challenge`,
`liability_shifted: true`, `eci 05`. Four independent sessions, 592 s / 609 s /
595 s during D2 and 594.6 s on `main` in this rerun — consistent with the 480 s
`POLL_DEADLINE_MS` plus the cell's own set-up, and not a flake. Root cause read
from source: the deadline branch of `PaymentViewModel.pollStatus` hardcodes
`Recovery.RETRY`, and the `Recovery` enum has no member meaning "unknown".

The cell **passes**, and the pass is the finding: `<any>` for the label plus hard
merchant assertions is precisely the shape that catches a wrong label over a
right outcome. Its pin asserts the bug on purpose — when #25 is fixed the cell
goes red, and that red is the fix arriving.

Two things must not be merged into it. Its sibling `airplane_during_challenge`
produces a label that *reads* the same and is **not the same result** — open
session, nothing succeeded, nothing shifted — so `failure:retry` is defensible
there. And **iOS is suspected on the same shape and is unmeasurable on a
simulator** (R6). That is a gap, not an acquittal, and the issue says so.

**For the integration guide:** a `retry` recovery on Android after a network
interruption is not proof the payment failed. Reconcile server-side before
re-collecting.

**#27, #28 and #31 are source findings, not measured ones**, and are filed as
such. No Amex card was run on either platform; no cell types a CVV before
selecting a stored card; and the sandbox emits only recoveries both SDKs
already know, so the `Recovery` divergence cannot be reached from a cell at all.
For #31 the practical consequence is worth stating: for an unknown recovery a
merchant sees `RecoveryDoNotRetry` on Android and `RecoveryUnrecognized(value)`
on iOS — **the same retry decision, a different Dart type.** Both platforms agree
in the other direction: an absent or empty recovery becomes `retry`.

### 4.2 SDK defects — iOS

| id | title | strength | status |
|---|---|---|---|
| [ios#14](https://github.com/paycross/payment-ios-sdk/issues/14) | 3DS E2E follow-ups: session-bounded re-arm, decline banner below fold, `change_method` copy, `os_log` | measured | open |
| [ios#16](https://github.com/paycross/payment-ios-sdk/issues/16) | Card form: the CVV numeric keypad cannot be dismissed | measured | open |
| [ios#17](https://github.com/paycross/payment-ios-sdk/issues/17) | 3-D Secure: rotating the device leaves the CVV keypad stuck on the challenge page | **measured, 2 reproductions + a controlled negative** | open |
| [ios#18](https://github.com/paycross/payment-ios-sdk/issues/18) | Saved-card picker has no accessibility identifiers, so a stored card can only be matched by its rendered label | measured + source | open |
| [ios#19](https://github.com/paycross/payment-ios-sdk/issues/19) | A saved Amex card cannot have its 4-digit CVV entered: `cvvBrand` is forced to `.unknown` on the saved-card path | **read from source** | open |

**#17 is scoped rather than overclaimed.** Rotating with the sheet up leaves the
CVV numeric keypad undismissable on the challenge page, where it covers the
bottom third — which is where the issuer-decline options sit. The SDK itself
survives the rotation and the dumps say so: the challenge is fully present after
the turn, `approve` is `visible="true"`, geometry correctly restored. Only the
keypad is stuck. The controlled negative is what makes it a finding rather than
a guess: an unrotated control on the same build minutes apart shows the keypad
present when the challenge appears and **absent** immediately after. It
certainly blocks automation; **whether a shopper can dismiss it by tapping the
challenge page is untested**, and the issue names that as the first thing to
check.

**#17 and the driver's own scroll bug are two different things and must never be
merged.** There were two distinct routes to "the CVV pad will not go on the ACS
page" during this campaign: this rotation-induced one, which is an SDK defect,
and a scroll-induced one in the test harness, which was the campaign's own bug
and is fixed. If a later triage merges them, a real defect gets written off as
harness error.

**#18 and #19 are parity findings.** #19's own source comment names Android's
`CardType.UNKNOWN`, so the Amex cap is parity on a defect rather than an
oversight on one side — it is fixed on both or the parity comment is wrong.

### 4.3 The accessibility finding that spans both platforms

**Neither platform lets you tap what you can name**, on the save-card control.
Measured on both, and both directions caught by probes rather than by reading:

| | Android | iOS |
|---|---|---|
| the save control | `CheckBox` with **empty `text` and empty `content-desc`** — no readable handle at all | `Switch` named `Save this card`, but **tapping the labelled row does nothing** |
| its label | a separate non-clickable `TextView` 300 px away, on the same line | carried by the row itself; only an unnamed inner control responds |
| what makes it findable | its `checkable`/`checked` state, and nothing else | its label |

The counter-case is what makes this a real distinction rather than a
coincidence: in the Android saved-card dropdown, tapping the label **does**
work — because there the label is a *child* of the clickable row and the touch
bubbles up. The save checkbox's label is a *sibling*, so the identical-looking
tap does nothing. That is a difference no source reading gives you.

This is filed as `ios#18` on the iOS side. The Android side is folded into
`android#26`'s theme — the SDK sets semantic handles that never reach the
accessibility tree — rather than filed separately.

### 4.4 Backend and contract findings

| id | title | strength | status |
|---|---|---|---|
| [io.paycross#870](https://github.com/paycross/io.paycross/issues/870) | Sandbox test card `…3055` no longer triggers a 3DS challenge (documented as challenge → decline) | measured | open |

**#871 is a prose contradiction, not a schema violation**, and the issue says
so. The schema declares `failure` as `["object","null"]` and does not require
it, so `failure: null` is schema-**valid**. What it contradicts is the field's
own documentation ("Populated when `status` is `failed`") and the formatter's
docblock. Filing it as a schema violation would have been wrong. The measured
case is `timeout_provider_never_answers`, which renders no `failure` block at
all on either platform.

The title's count of **five** call sites is the issue's own and is reproduced
here verbatim; **this report has not independently verified it.** The campaign's
own D2 notes disagree with themselves about whether it is five or three — they
say the two `RecoverStuck*` commands set `AUTHORIZED` rather than `FAILED`, and
then count those two among the five. Re-deriving the number belongs with
whoever fixes the issue.

### 4.6 Not a finding — the rig faults

Three failures during this campaign looked like SDK findings and were not. They
are recorded because each produced a durable rule (Appendix A), and because a
future triage will meet their shapes again.

* **Android token entry lost 4–7 characters of a 1011-character session token**
  on three consecutive cells including the interleaved control, inside the
  driver, before the SDK was asked anything. The emulator had been up 15 h 55 m;
  a cold restart cleared it. Caught by the driver's own read-back guard doing
  exactly its job — without it, a truncated token surfaces as an instant HTTP
  401 and reads as an SDK bug. Not filed.
* **A `FATAL EXCEPTION: UiAutomation` scored a substantively green cell as a
  failure.** The crash was the driver's own `uiautomator dump` — `app_process`,
  `Bad file descriptor`, no app frame in the stack and no `Process:` line, which
  is what sent the verifier to its conservative "blame the app" default. Fixed
  in the runner (PR #38), with that dump as the fixture. Not filed against the SDK.
* **An ANR during `type_cvv` on the saved-card path** reported itself as "the
  sandbox ACS page never appeared" while the session had zero transactions and
  no page was ever due. The ANR's own CPU table is the discriminator: app 2.1%
  user / 84% kernel, the IME 78% kernel, the graphics composer 98% kernel. A
  genuine main-thread block in the SDK burns **user** time. One observation, rig,
  nothing filed.

### 4.7 Open by design — the label that names a transaction the session does not have

`session_expired_server_submit` is the only live discovery sentinel left in the
matrix. **Reproduced four times: on both platforms in two independent runs**,
every one of them `session_status: expired` with `transactions: []` and a
non-empty `<txn>` in the label.

Both SDKs **refuse correctly** — no money moves on a dead session, and the
verdicts for this cell were fixed before it was ever run so the answer could not
be fitted to it. The finding is narrower and stranger: the label names a
transaction id that the merchant API does not list against the session.

The cause is **unmeasured, and this rerun could not measure it.** The chain read
from source — `POST /api/submit-card` apparently accepting a card on an expired
session and handing back a transaction id that is never recorded against the
session — is inference plus two measured endpoints. The submit and status HTTP
bodies were never captured, because the runner does not capture them. So a
rerun adds observations of the *symptom* and no evidence about the *cause*.

**Nothing is filed, on purpose, and the verification step is small and exact:**

> Capture the `POST /api/submit-card` response and the first `GET /status/{id}`
> response for this cell. If the submit really answers `success: true` on an
> expired session, that is a `paycross-core` issue in the same family as
> io.paycross#871 — two read paths disagreeing about one transaction.

Until then the cell keeps its `<any>` sentinel, and that is a documented reason
rather than an oversight: pinning `result:failure:restart:<txn>` would make the
runner assert that the captured id names a transaction on the session, and it
does not. **The label naming a transaction that does not exist is the thing to
fix — in the SDKs, not in the cell.**

The tooling half of this is already closed. `label_transaction_notes` records
the mismatch on every discovery cell (PR #37), so the class of defect that took
a hand read of `merchant.json` to notice is now machine-recorded.

## 5. D6 — version floors: pending, not measured

**D6 has not run.** Its owner prerequisites are outstanding and no part of this
report should be read as covering version floors. This section states what will

Six variants, D0 (6 cells) each:

| variant | Flutter | platform runtime | result |
|---|---|---|---|

Three specific things D6 exists to catch, named now so the run is not read
loosely afterwards:

* **The build itself is half the test.** The pubspec claims
  `sdk: ^3.12.2, flutter: '>=3.44.2'`, and 3.44.2 is genuinely the oldest stable

## 6. Residual risks

Stated plainly rather than buried. Each of these is a thing this campaign did
not prove, with the reason it could not.

1. **iOS release behaviour is proven only as far as building and linking.**
   Flutter refuses any non-debug build for the iOS simulator — verified by
   running it, not only by reading the tool source — so every iOS cell in this
   report ran against a **debug** binary. Android is where the real risk lives,
   because R8 rewrites bytecode and iOS has no equivalent transformation of the
   SDK's `Intent` payload, and the Android half **is** fully exercised. Closing
   the iOS half needs a physical device through TestFlight, which is a stated
   campaign non-goal.

2. **`android#25` is unmeasured on iOS, and that is a gap rather than an
   acquittal.** Every network-cut cell is Android-only (R6): the iOS simulator
   shares the host's network and every route to cutting it needs sudo or the
   GUI. The iOS source predicts the same shape; the issue says so and does not
   claim more.

3. **The submit-endpoint question is open.** Whether `POST /api/submit-card`
   accepts a card on a server-expired session is unproven — see §4.7. The
   verification step is named and belongs to whoever next has the rig.

4. **Version floors are entirely unmeasured.** See §5. This report covers API 35
   and iOS 26.5 only.

5. **`data.wallets.google_pay = false` has no per-session route** on this TEST
   merchant — it is computed once at session creation from a merchant extra
   attribute and never rebuilt. The absence cell exists only because the
   `account_funding` route turned out to be open; testing the wallet-disabled
   merchant configuration needs a second TEST merchant.

6. **The Google Pay button's only usable handle belongs to Google.** The SDK's
   own `testTag` never reaches the accessibility tree, so the rig matches Play
   services' string, which moves with the GMS version and the locale. Every D4
   result is pinned to one GMS build at one moment (`android#26`).

7. **The plugin's Android detach path is unmeasured.** `dont_keep_activities` is
   **inert** on this emulator — the setting is written and reads back as `1`, and
   the activity manager ignores it, measured three ways including across a
   reboot. `kill_activity` does not reach the path either (a force-stop takes the
   process, so no code runs) and a configuration change does not (R11: the
   example app absorbs its own). So both `onDetachedFromActivity` finishing a
   pending call with `paycross_result_unknown` **and** the follow-on that then
   drops the real result because `pending` is already null are carried on source
   reading alone. The runner's tolerated-marker machinery built for this is
   correct, tested, and currently has no user. Both facts belong here.

8. **Flutter hot restart with the sheet up: attempted and blocked, not a
   result.** Four attempts. The fourth got furthest and failed structurally:
   `flutter run` reaches the Dart VM Service through an adb port forward whose
   host end binds on the Windows loopback, while Flutter runs in WSL and connects
   to WSL's loopback — different network namespaces, proven in both directions on
   three leftover forwards. **No longer deadline can help.** The source predicts
   that a hot restart delivers no label at all, that the sheet stays payable, and
   that the next `presentPayment` answers `error:busy` until the orphaned sheet
   frees the native slot — **that prediction is deliberately not written up as
   though it had been checked.** The remedy is host-level (WSL2 mirrored
   networking) and is named rather than done.

9. **The documented empty-`transactionId` success is unmintable** on this
   sandbox, so that documented shape is unexercised.

10. **A long background is a documented risk, not a tested one.** iOS's poll
    deadline uses a clock that advances while the process is suspended, against
    a 480 s budget. D3's background cells stay well under that at 60 s.

11. **A shopper can kill the app mid-challenge and the app will never learn the
    outcome**, on either platform. Nothing is broken — the pending call lives in
    the Dart isolate and dies with the process, and the reconciliation duty is
    server-side. But a merchant integrating this SDK needs telling, rather than
    discovering it.

12. **Seven of the eight `PayCrossErrorCode` values are asserted from source,
    not exercised** — `notConfigured`, `testPrefillInProduction`, `busy`,
    `noActivity`, `noPresenter`, `resultUnknown` and the mapper's `unknown`
    fallback. `lib/src/errors.dart` declares eight members and only
    `invalidToken` is reachable from a cell. `testPrefillInProduction` needs
    `PayCrossEnvironment.production` and this campaign never touches PROD.

13. **`android#27`, `#28`, `#31` and `ios#19` are source findings.** No Amex card
    was run; no cell types a CVV before selecting a stored card; no unknown
    recovery is emitted by the sandbox.

14. **The SDK contract under real release signing across the matrix is
    unproven**, and this is a distinct gap from the release-build one. Real
    signing plus R8 is proven on the *published* demo APK by a human-driven
    scenario; R8 and resource shrinking leaving the contract intact is proven by
    a control cell against a *locally built, debug-signed* automation APK. The
    matrix running against a real-signed automation build needs a keystore
    passphrase at build time and is owner/CI territory.

15. **Anything on PROD.** By design, on every dimension, at every point.

## 7. Production readiness — the launch blocker

This is not a test result. It is deployment state, and it belongs in this report
because it gates the same launch this campaign is evidence for.

**The system is not live.** There are zero production merchants; the first
merchant onboards at the Flutter SDK launch. The wallet-path gap discovered on
2026-08-28 is therefore a **launch blocker, not an outage**.

Before the first merchant, the production wallet path needs three things
**shipped together**:

1. the **vault standup** — the production terraform carrying
   `DECRYPT_WALLET_API_URL` exists only on an unmerged branch;
2. a **post-wallet `paycross-core` deploy** — production was last deployed
   2026-07-31, before the wallet work;
3. **`DECRYPT_WALLET_API_URL` on the card handler**, whose vault-decrypt edge
   shipped to production on 2026-08-28 without the other two.

Ship any one of them alone and the wallet path is still broken. This is recorded
as a launch-checklist item; a live read of the production Lambda environment to
confirm it was **deliberately dropped** as belt-and-braces, because the
deployment evidence stands without it. It is stated here at that strength: read
from deployment state and branch state, not from a production probe.

## Appendix A — rig lessons

Every one of these cost a misdiagnosis before it became a rule. They are here so
the next campaign pays for them once.

**Never diagnose Android connectivity with `ping`.** This emulator's user-mode
NAT does not forward ICMP, so `ping` reports 100% packet loss whether the
network works or not — confirmed on a freshly booted emulator where ping fails
and a TCP connect to the API on 443 succeeds. An entire "the emulator lost the
network" diagnosis was built on that reading, and the failed instance was
destroyed before TCP was ever tested on it. Use a TCP connect.

**Wait for the load average to settle after an emulator boot.** A rerun started
into a post-boot storm at load average **18.63** and was killed four seconds in.
It fell 14.24 → 10.79 → 7.73 → 5.53 → 3.96 → 2.84 → 2.03 → **1.45**, and the run
that started then was green. Recognise the artifact a killed start leaves: a run
directory with only a `report.json` and no `progress.jsonl`.

**Long emulator uptime drops `input text` chunks.** After 15 h 55 m up, three
cells in a row — including the interleaved control — lost 4–7 characters of a
1011-character token inside the driver. Free memory was *higher* than in the
healthy run; uptime was the variable that changed. A cold restart fixed it. Keep
the read-back guard: without it this surfaces as an instant HTTP 401 and reads
as an SDK bug.

**A host suspend is nastier than a reboot, because nothing dies.** The monotonic
clock does not advance across a WSL sleep, so `timeout` never fires, `ps`
under-reports elapsed time by the whole sleep, and a run thaws mid-driver-call
against sessions minted hours earlier — failing with a plausible, sandbox-shaped
message. The tell was one unasserted field: `seconds: 23963` against
`budget_seconds: 1446`. Now a permanent per-cell guard that **fails** the cell
saying "rerun", deliberately rather than warning: a thawed cell fails
plausibly.

**Mac rig: three separate blockers, each looking like the others.** The login
keychain relocks and must be unlocked *and* have codesign on the key partition
list (never with the password on the command line). The only WWDR intermediate
present was the 2013 G1, expired 2023 — both codesigning identities existed and
were key-paired but **invalid**, which `find-identity` shows only with `-v`;
installing the public G3 intermediate produced two valid identities. And
WebDriverAgent's build directory does not survive a Mac restart, so WDA has to
be rebuilt before an iOS run rather than assumed.

**`git tag --contains` and `git merge-base --is-ancestor` are invalid against a
squash-merged PR.** The commits are not ancestors, so both answer "no" while the
fix is plainly on `main`. This nearly aborted one correct release run and caught
two later agents. **Verify by content** on the target tree, not by ancestry.

**Deployed is not source.** A page redesign authored 2026-04-13 reached TEST on
2026-08-31, mid-campaign, and broke every Android challenge cell. For four
months, reading `origin/main` would have shown the new markup while the rig
passed against the old deployed page, and nothing on either side could tell.
The durable form: **checking `origin/main` is not the same as checking what is
running.** The robust matcher is an accessibility *identifier* owned by our own
SDK — iOS matches `threeDSCancel` and was untouched by the re-skin; page-text
matching is the fragile pattern, and where it is unavoidable, carry every
wording you have seen, because deployments lag.

**One device, one runner — and the lease protects you from other agents, not
from yourself.** Two agents colliding on one emulator produced fake
`FATAL EXCEPTION … UiAutomationService already registered` lines and a discarded
run; re-read the lease table in the same breath as writing to it, because a
check from four minutes ago is not a lock. Separately, three iOS runs failed on
a leaked WebDriverAgent session that was the agent's **own** duplicate process.
`pgrep` for your own runner before declaring a device broken; an empty log is no
evidence a process died.

**A watcher that only reports is safe to leave armed; a watcher that ACTS must
be killed the moment its window closes.** One left armed was a single process
exit away from launching an unleased run, hours later, on a device another agent
had claimed. It outlives your attention, and no lease can see it.

**Prove the behaviour, not the request.** `dont_keep_activities` reads back as
`1` and does nothing on this image; an airplane-mode broadcast flipped a setting
while the radios stayed up. Both produced, or would have produced, a green cell
that observed nothing. The runner now fails a cell whose declared tolerated
marker never appears — the empty-list tell.

**Before believing any `FATAL EXCEPTION`, ask whose it is.** A `Process:`-less
`UiAutomation` crash from `app_process` with no app frame in the stack is the
harness, not the app. And the two look-alikes must not be merged: the collision
case carries `UiAutomationService … already registered`; this one does not.
